
Глубокий анализ асинхронного RAG-сервиса на масштабе High-Load требует разбора критических пограничных случаев (edge cases), которые часто ломают систему в продакшене. Пройдемся по пяти основным категориям корнер-кейсов: от «призраков» в базах данных до уязвимостей в многопользовательском доступе.
1. Индексация: Проблема «Призраков» и Гонка Документов
Чанки-призраки (Ghost Chunks) при обновлении документа
Кейс: Пользователь загрузил doc_1, система разбила его на 100 чанков с ID от uuid5(doc_1:idx:0) до uuid5(doc_1:idx:99). Затем пользователь отредактировал документ, сильно сократив его, и отправил на переиндексацию. Новый файл разбился всего на 40 чанков (от idx:0 до idx:39).
Проблема: Чанки со старыми детерминированными UUID с 40 по 99 останутся в Qdrant навсегда, так как upsert перезапишет только первые 40. Пользователи будут получать в ответах куски старого, удаленного текста.
Решение: Перед повторной индексацией документа (или в начале транзакции) необходимо явно вызывать очистку векторной базы по фильтру: delete(collection, filter={"doc_id": doc_1}).

Состояние гонки (Race Condition) при быстрой перезагрузке
Кейс: Пользователь дважды нажал кнопку «Обновить документ» в интерфейсе, или два воркера параллельно схватили сообщения об обновлении одного и того же doc_1 из RabbitMQ.
Проблема: Первый воркер удаляет старые чанки и начинает писать новые. Второй воркер параллельно делает то же самое. На выходе в Qdrant может записаться смесь чанков, либо операция удаления одного воркера сотрет данные, только что записанные вторым воркером.
Решение: Внедрение распределенной блокировки (Distributed Lock) в Redis на время индексации конкретного файла: redis.set(f"lock:ingest:{doc_id}", "true", nx=True, ex=300). Если замок занят, сообщение возвращается в очередь (nack с requeue=True).

2. Поиск и LLM: Обрезка контекста и лимиты токенов
Смерть контекста из-за "Мусора" в RRF/BM25
Кейс: Включен гибридный поиск (SEARCH_HYBRID=true). Пользователь вводит запрос, содержащий популярное стоп-слово или внутренний термин (например, название компании «Ромашка»), которое встречается в каждом документе.
Проблема: Полнотекстовый индекс (BM25) вернет топ-50 чанков, забитых нерелевантным мусором, содержащим слово «Ромашка». Алгоритм RRF сольет их с валидными векторными результатами. Если лимит токенов контекста жесткий, этот «шум» вытеснит действительно важные релевантные чанки, и LLM ответит галлюцинацией.
Решение: Настройка строгого порога отсечения (score threshold) для текстового поиска, очистка стоп-слов на этапе предобработки запроса и динамическое вычисление размера контекста перед отправкой в LLM.

Изменение модели эмбеддингов в рантайме
Кейс: Вы поменяли в .env модель EMBEDDING_MODEL с multilingual-e5-small на более мощную (например, bge-m3), у которой другая размерность векторов (например, 1024 вместо 384).
Проблема: Старые векторы в Qdrant имеют размерность 384. При первой же попытке нового query-воркера сделать поиск по вектору размерностью 1024 Qdrant выбросит gRPC Error (размерности не совпадают), полностью парализовав RAG-сервис.
Решение: У вас в коде уже есть маркер embedding_model в точках и логирование предупреждения. Для High-Load этого мало. Сервис должен автоматически падать при старте (Fail-Fast паттерн), если размерность модели из конфига не совпадает с параметрами существующей коллекции в Qdrant. В идеале — создавать новую коллекцию с префиксом версии (например, documents_v2).

3. Безопасность и ACL: Уязвимости токенов и AD-шторм
Атака через подмену модели (LLM Request Hijacking)
Кейс: Злоумышленник перехватил JWT-токен обычного пользователя и отправляет в query_queue кастомный payload, где вручную прописывает тяжелую и дорогую модель (например, gpt-4-32k или claude-3-5-opus), выставляя LLM_TEMPERATURE=2.0.
Проблема: Если ваш сервис слепо доверяет полям llm_model и llm_provider из тела сообщения (аргументируя это per-request роутингом), злоумышленник может за пару минут исчерпать ваш баланс API (бюджет) или заспамить LLM-провайдера так, что легитимные пользователи упрутся в Rate Limits.
Решение: Роутинг моделей должен быть строго валидируемым. TokenValidator должен проверять не только подпись JWT, но и сопоставлять sub (user_id) или groups со списком разрешенных ему моделей. Обычный пользователь не должен иметь технической возможности вызвать модель, отличную от базовой.

Раздувание Active Directory (Token Bloat & AD Storm)
Кейс: Система развернута в гигантской корпорации. У пользователя в JWT-токене (в claim groups) зашито 800+ групп доступа Active Directory.
Проблема 1: Размер самого JWT-токена начинает превышать лимиты заголовков и буферов RabbitMQ/HTTP (токен весит более 8-16 КБ).
Проблема 2: При поиске в Qdrant массив условий access_group IN (группа_1, группа_2, ... группа_800) превращается в тяжелую вычислительную задачу для векторного индекса, увеличивая latency поиска с 5мс до 300мс.
Решение: Отказаться от передачи всех групп внутри JWT. В токене передавать только ID пользователя, а список его групп кэшировать в Redis на стороне воркера со сжатием (например, через Bloom Filter или компактный Set) и подтягивать локально при валидации сообщения.

4. Инфраструктурные сбои и Асинхронность
Каскадный сбой кэша (Cache Stampede / Thundering Herd)
Кейс: Популярный документ (например, «Новая политика отпусков 2026») часто запрашивается сотрудниками. В 9:00 утра истекает TTL кэша для ответов по этому документу в Redis.
Проблема: В 9:01 сотни пользователей одновременно задают похожие вопросы. Происходит кэш-мисс. Сотни тяжелых асинхронных запросов одновременно летят в Qdrant и, что хуже, параллельно генерируют сотни дублирующих запросов к LLM API. Ваша система мгновенно ловит бан от OpenAI/DeepSeek по причине Rate Limit Exceeded.
Решение: Использование вероятностного вытеснения (XFetch алгоритм) или блокировок на уровне генерации (Mutex). Если воркер видит, что кэша нет, он ставит локальный замок в Redis: «Я уже считаю этот ответ, остальные — подождите 2 секунды или возьмите старый кэш из Stale-состояния».

Проблема Потери Сообщений в RPC-паттерне (Orphaned Responses)
Кейс: query_queue приняла запрос, RetrieverService нашел контекст, LLM сгенерировала ответ и воркер пытается отправить его обратно через reply_to (клиент ждет ответа по схеме RPC). В этот микросекундный момент клиентское приложение (например, бэкенд чат-бота) перезагрузилось или отвалилось по таймауту.
Проблема: Очередь ответа (reply_to) удалена или закрыта. Асинхронный воркер падает с ошибкой публикации, сообщение падает в DLX, но пользователь в интерфейсе видит вечную загрузку. При этом ресурсы (деньги на LLM, CPU воркера) уже потрачены впустую.
Решение: Использовать паттерн Fire-and-Update со статусной моделью в Postgres. Клиент не ждет RPC-ответа в том же соединении, а слушает веб-сокет или опрашивает (polling) таблицу conversations. Воркер сначала пишет готовый ответ в Postgres/Redis, а затем шлет легкое уведомление: «Запрос query_id_123 готов».

🛠️ Что проверить в коде прямо сейчас:
shared/pii.py: У вас включена анонимизация (ANONYMIZE_CONVERSATIONS=true). Проверьте регулярные выражения. Если пользователь введет технический текст, похожий на маску карты (например, конфигурационный ID в формате 1234-5678-...), не вырежет ли его регулярка, сломав тем самым смысл контекста для RAG?
infrastructure/llm/: Задан ли жесткий timeout (например, 15-30 секунд) на асинхронные HTTP-запросы к DeepSeek/OpenAI? Без таймаута, если API провайдера «зависнет» (будет держать соединение открытым, но не присылать токены), ваш асинхронный воркер будет бесконечно держать задачу открытой, расходуя пул соединений.







1. Слой хранения: Асинхронный пул и деградация PostgreSQL
Пул соединений при всплесках нагрузки (Connection Pool Exhaustion)
Кейс: Сервис масштабируется. Вы запустили 20 реплик query-воркеров для обработки шквала вопросов. Каждый воркер при старте инициализирует пул через SQLAlchemy + asyncpg.
Проблема: По умолчанию пул может открывать до 10–20 соединений к базе. В итоге 20 воркеров попытаются открыть 20 * 20 = 400 параллельных сессий к PostgreSQL. Если в postgresql.conf параметр max_connections выставлен в дефолтные 100, новые воркеры начнут падать с ошибкой Too many connections, а старые — зависать на этапе ожидания свободной сессии (I/O блокировка), сваливая healthcheck-сервер.
Решение:В конфигурации SQLAlchemy жестко ограничить размеры пула для воркеров: pool_size=3, max_overflow=2 (воркеру обработки очереди не нужно много соединений, он обрабатывает сообщения последовательно или небольшими батчами).
Использовать асинхронный балансировщик соединений PgBouncer в режиме транзакций (pool_mode=transaction).



Зависание транзакций при обрыве связи с LLM
Кейс: Воркер берет сообщение, открывает асинхронную транзакцию в Postgres, обновляет статус беседы в conversations на processing и делает сетевой запрос к LLM (DeepSeek/OpenAI). Сеть между вашим сервером и OpenAI начинает «моргать», пакеты теряются.
Проблема: Если на клиенте LLM не выставлен жесткий timeout, а транзакция Postgres остается открытой (ждет завершения функции, чтобы сделать commit), в базе начинает расти число «незавершенных транзакций» (Idle in transaction). Это блокирует очистку старых строк (VACUUM), приводит к раздуванию (bloat) таблиц и блокирует другие пишущие запросы.
Решение: Никогда не держать транзакцию открытой во время сетевых запросов к сторонним API. Схема должна быть атомарной: открыть транзакцию -> обновить статус беседа сохранен -> закрыть транзакцию (commit) -> уйти в долгий сетевой запрос к LLM -> открыть новую транзакцию -> записать ответ -> закрыть транзакцию.

2. Слой LLM: Специфика стриминга токенов (Streaming Edge Cases)
Разрыв соединения посреди генерации (Partial Generation Loss)
Кейс: Вы включили асинхронный стриминг ответов от LLM (stream=True), чтобы отдавать токены пользователю чанками в реальном времени. На 150-м токене из 500 сеть падает или падает клиентский подпищик.
Проблема: Воркер перехватил исключение разрыва связи, но в базу conversations записывать нечего — финальный текст ответа не сформирован, так как стрим оборвался. Пользователь повторит запрос, но система потеряла контекст того, что успела выдать.
Решение: Внутри асинхронного цикла чтения стрима async for chunk in response аккуратно накапливать приходящие токены в буфер (строку). В блоке finally или при пойманой ошибке связи записывать в базу то, что успело сгенерироваться, добавив техническую метку [генерация прервана]. Это спасет историю контекста для последующих запросов.

Проблема Backpressure на стороне WebSocket/SSE клиента
Кейс: LLM выдает токены с огромной скоростью (особенно локальные модели на vLLM/Ollama). Воркер пересылает эти токены в UI-клиент через WebSockets или Server-Sent Events (SSE). Браузер пользователя или мобильное устройство зависло (например, из-за тяжелой отрисовки интерфейса).
Проблема: Скорость генерации выше, чем скорость чтения клиентом. Асинхронный буфер отправки воркера начинает бесконечно раздуваться в оперативной памяти, ожидая, пока сетевой стек протолкнет данные. Это приводит к скрытой утечке памяти воркера во время стриминга.
Решение: Контролировать размер буфера отправки и выставлять таймауты на запись в сокет. Если клиент не успевает вычитывать токены в течение 3–5 секунд — принудительно обрывать генерацию на стороне LLM (вызывать .close() у асинхронного генератора), экономя деньги и ресурсы.

3. Индексация: Мультимодальность и таблицы
Разрушение разметки больших таблиц в HTML/Markdown
Кейс: У вас заявлено: «таблицы сохраняются с HTML-структурой, элементы тегируются». Воркер парсит документ, натыкается на огромную таблицу (например, финансовый отчет на 2 листа).
Проблема: Если парсер засунет всю HTML-структуру огромной таблицы в один чанк, он превысит лимит токенов эмбеддинга (обычно 512–1024 токена). Модель эмбеддингов просто обрежет хвост таблицы, и данные из нижних строк никогда не превратятся в корректные векторы. Если же парсер порежет HTML-код таблицы жестко по символам посередине, структура тегов <table><tr><td> нарушится. На этапе сборки контекста LLM получит битый HTML-код, сойдет с ума и выдаст неверные цифры.
Решение: Для таблиц нужен специализированный чанкер. Таблицы нельзя резать посимвольно. Их необходимо разбивать построчно, дублируя строку заголовка (header) в каждый чанк: Чанк = [Заголовок таблицы] + [Строка 45] + [Строка 46].

4. Очереди: Бесконечный цикл ошибок (Poison Pill & Retry Loop)
Проблема бесконечного ретрая "ядовитых" сообщений (Poison Pills)
Кейс: Пользователь загрузил битый PDF-файл (например, зашифрованный или с поврежденной структурой заголовков). Сообщение падает в ingest_queue. Воркер пытается его распарсить, библиотека unstructured падает с жестким исключением ValueError.
Проблема: Реализован механизм Retry с exponential backoff. Сообщение возвращается в очередь, ждет, снова берется воркером и снова падает. Если в коде обработки ошибок допущена неточность (например, ошибка не логируется как фатальная), это сообщение будет циркулировать в системе днями, забивая логи, тратя CPU и мешая обработке валидных документов.
Решение: Жестко разделять типы ошибок.Инфраструктурные ошибки (упал MinIO, таймаут Qdrant) — отправлять на Retry с backoff.
Программные/Валидационные ошибки (битый файл, неверный формат JWT, неизвестное поле) — немедленно отправлять в Dead Letter Exchange (DLX) без единого ретрая, уведомляя пользователя через статус базы данных failed_invalid_file.

Чтобы защитить проект от этих проблем, в вашей DI-системе (dishka) логика управления транзакциями и таймаутами должна выглядеть следующим образом:

# Пример безопасного выполнения I/O операций вне контекста долгой транзакции БД
async def handle_query_pipeline(msg_payload, db_session_provider, llm_client):
    # 1. Быстрая атомарная транзакция: проверка и фиксация статуса
    async with db_session_provider() as session:
        conversation = await session.get(Conversation, msg_payload["id"])
        conversation.status = "processing"
        await session.commit() # ТРАНЗАКЦИЯ ЗАКРЫТА, Postgres свободен

    # 2. Сетевые I/O операции с жесткими ограничениями
    try:
        # Устанавливаем лимит на работу с LLM, чтобы не зависнуть вечно
        async with asyncio.timeout(30.0): 
            context = await vector_store.search(msg_payload["query"])
            # Сборка буфера стрима
            full_response = ""
            async for chunk in llm_client.generate_stream(msg_payload["query"], context):
                full_response += chunk.text
                await send_to_websocket_or_queue(chunk.text)
                
    except asyncio.TimeoutError:
        full_response = "[Ошибка: Превышено время ожидания ответа от ИИ-провайдера]"
    except Exception as e:
        full_response = f"[Критический сбой генерации: {str(e)}]"

    # 3. Открываем вторую быструю транзакцию для сохранения финала
    async with db_session_provider() as session:
        conversation = await session.get(Conversation, msg_payload["id"])
        conversation.response = full_response
        conversation.status = "completed"
        await session.commit()







1. Архитектура asyncio: Проблема «Голодания» Event Loop (Loop Starvation)
Очередь микро-блокировок в асинхронном JSON-парсинге
Кейс: На High-Load в query_queue прилетают сотни запросов в секунду. Каждый запрос содержит JWT-токен, метаданные и историю переписки. Воркер использует стандартный встроенный модуль json (или встроенные механизмы Pydantic 1.x) для десериализации payload и валидации через pydantic-settings.
Проблема: Десериализация больших JSON-строк и валидация схем в Python — это чисто CPU-bound операция. Хотя один вызов json.loads() занимает пару миллисекунд, при высокой плотности запросов сотни таких вызовов создают «микро-серию» блокировок. Event loop начинает «заикаться» (Loop Starvation). Из-за этого сетевые пакеты aio-pika (RabbitMQ) не успевают вовремя подтверждаться (ACK), брокер считает, что воркер умер, и начинает массово закрывать TCP-каналы по таймауту (Heartbeat timeout).
Решение:Замените стандартный JSON-парсер на orjson или msgspec. Они написаны на C/Rust, работают в 5–10 раза быстрее и практически не блокируют поток.
Переведите Pydantic на версию 2.x (где ядро валидации написано на Rust и выполняется мгновенно).



2. Слой СУБД и Очередей: Проблемы деградации диска и памяти
Раздувание WAL-логов и индексов при Soft-Delete документов
Кейс: У вас реализована очистка документов: «Удаление документов (soft-delete + очистка векторов, опционально файла)». В системе идет активный документооборот: в день загружается и помечается удаленными (soft-delete) по 100 000 документов.
Проблема: При soft-delete физические строки в PostgreSQL остаются на диске, просто меняется флаг (например, is_deleted = true). Полнотекстовый индекс базы данных и стандартные B-Tree индексы продолжают хранить ссылки на эти строки. 1. Архитектура asyncio: Проблема «Голодания» Event Loop (Loop Starvation)
Очередь микро-блокировок в асинхронном JSON-парсинге
Кейс: На High-Load в query_queue прилетают сотни запросов в секунду. Каждый запрос содержит JWT-токен, метаданные и историю переписки. Воркер использует стандартный встроенный модуль json (или встроенные механизмы Pydantic 1.x) для десериализации payload и валидации через pydantic-settings.
Проблема: Десериализация больших JSON-строк и валидация схем в Python — это чисто CPU-bound операция. Хотя один вызов json.loads() занимает пару миллисекунд, при высокой плотности запросов сотни таких вызовов создают «микро-серию» блокировок. Event loop начинает «заикаться» (Loop Starvation). Из-за этого сетевые пакеты aio-pika (RabbitMQ) не успевают вовремя подтверждаться (ACK), брокер считает, что воркер умер, и начинает массово закрывать TCP-каналы по таймауту (Heartbeat timeout).
Решение:Замените стандартный JSON-парсер на orjson или msgspec. Они написаны на C/Rust, работают в 5–10 раза быстрее и практически не блокируют поток.
Переведите Pydantic на версию 2.x (где ядро валидации написано на Rust и выполняется мгновенно).

1. Слой брокера сообщений: Патологии RabbitMQ и aio-pika
Проблема скрытого дублирования при «Аварийном завершении» (At-Least-Once Delivery Side-Effects)
Кейс: query_queue обрабатывает сложный запрос. RetrieverService отработал, LLM генерирует ответ. Из-за пиковой нагрузки на ноду Kubernetes, ОС убивает контейнер воркера по лимиту памяти (OOMKilled) прямо в процессе генерации, до того как воркер успел отправить message.ack().
Проблема: RabbitMQ видит обрыв TCP-соединения с воркером. Так как сообщение не было подтверждено (ack), брокер мгновенно возвращает его в начало очереди (requeue=True). Новый поднявшийся воркер забирает это же сообщение и начинает обрабатывать его заново. Если сбой был вызван структурой самого запроса (например, «тяжелый» контекст, вызывающий OOM), система уйдет в бесконечный цикл перезагрузок воркеров (OOM Crash Loop), парализуя всю очередь.
Решение:Ограничить количество повторных доставок сообщения на уровне RabbitMQ с помощью плагина rabbitmq_delayed_message_exchange или контролировать поле заголовка x-delivery-count (если оно больше 3 — принудительно отправлять сообщение в DLX).
Использовать idempotency_key (в качестве которого выступает query_id или хэш токена + запроса), фиксируя статус «в обработке» в Redis со сверхкоротким TTL. При повторном получении сообщения с флагом redelivered=True воркер проверяет замок и, если он есть, сразу дропает сообщение в DLX.



Блокировка брокера при переполнении диска (RabbitMQ Resource Alarms)
Кейс: Поток документов в ingest_queue резко увеличился. Воркеры background-очереди не успевают их вычитывать, и сообщения начинают скапливаться в RabbitMQ. Каждое сообщение содержит файл (или ссылку) и метаданные.
Проблема: По умолчанию, если объем сообщений в очередях RabbitMQ начинает занимать много оперативной памяти или дискового пространства, срабатывает встроенный механизм Resource Alarm. Брокер переходит в режим Blocked и полностью прекращает принимать новые сообщения от API-продюсеров (все await channel.default_exchange.publish() начинают зависать по таймауту). API-слой начинает отвечать пользователям ошибками 504 Gateway Timeout.
Решение:В очередях никогда не передавать бинарное содержимое документов (файлы). В RabbitMQ должен лежать только плоский JSON с UUID документа и ссылкой на бакет в MinIO.
Настроить лимиты очередей (x-max-length или x-max-bytes) с политикой reject-publish или drop-head, чтобы брокер корректно сообщал API о перегрузке, позволяя применить паттерн Rate Limiting (429 Too Many Requests) на стороне шлюза.



2. Слой ИИ-генерации: Специфика DeepSeek / OpenAI API под нагрузкой
Проблема «Дырявого» лимита токенов в контексте (Prompt Truncation / Sliding Window)
Кейс: Пользователь ведет очень долгий диалог в рамках одной conversation_id. На сотом шаге история сообщений + системный промпт + извлеченные чанки из Qdrant в сумме начинают превышать контекстное окно модели (например, вышли за рамки 32k/64k/128k токенов).
Проблема: Разные провайдеры ведут себя по-разному. Одни (как OpenAI) возвращают ошибку 400 ContextWindowExceeded. Другие (некоторые провайдеры vLLM или кастомные эндпоинты) молча обрезают начало промпта (включая системные инструкции безопасности или первые системные чанки), чтобы втиснуть запрос в окно. В итоге модель «забывает», что она должна отвечать строго по контексту, и начинает безудержно галлюцинировать.
Решение: Внедрить обязательную асинхронную токенизацию на стороне воркера с помощью библиотеки tiktoken или transformers.AutoTokenizer. Перед отправкой запроса в LLM воркер должен посчитать точную длину промпта. Если она превышает лимит, необходимо динамически выкидывать из контекста самые старые сообщения истории или чанки с наименьшим релевантным скором (алгоритм скользящего окна токенов).

3. Слой векторного поиска: Деградация памяти Qdrant
Фрагментация оперативной памяти при агрессивном обновлении Payload
Кейс: Сервис активно обновляет метаданные чанков в рантайме (например, меняются группы доступа access_group в рамках синхронизации с Active Directory через скрипты manage_groups.py). Вы вызываете set_payload или overwrite_payload для существующих точек в Qdrant.
Проблема: Qdrant активно использует memory-mapped файлы (mmap) и структуры в RAM для обеспечения миллисекундного поиска. Частое обновление и удаление payload (особенно текстовых полей) приводит к внутренней фрагментации памяти движка. Виртуальная память (VIRT/RES в top), занимаемая процессом Qdrant, начинает расти, даже если физическое количество точек остается неизменным. На серверах с жестким лимитом RAM это гарантированно приводит к падению Qdrant.
Решение: В конфигурации коллекции Qdrant настроить более агрессивные параметры для оптимизатора сегментов (indexing_threshold_kb, flush_interval_sec). Также на уровне инфраструктуры необходимо заложить регулярное выполнение команды Clear Payload Space через вызов оптимизации (Segment Rebuilding).

4. Пограничные случаи JWT-авторизации сообщений

Проблема: Чтобы проверить каждый такой токен, TokenValidator воркера вынужден делать асинхронный запрос к Redis (await redis.get(...)). Из-за шквала запросов пул соединений с Redis исчерпывается. Решение: Изменить порядок проверок в TokenValidator. Сначала всегда проверять валидность структуры, exp-тайм и криптографическую подпись токена локально на CPU. И только если подпись верна и токен еще не истек, делать точечный запрос в Redis Blacklist для проверки на отзыв. Это отсечет 99% мусорного спама без единого сетевого запроса к Redis.

import tiktoken
import structlog
from src.domain.exceptions import ContextOverflowException

logger = structlog.get_logger()

class AdvancedContextManager:
    def __init__(self, model_name: str = "gpt-4o-mini", max_context_tokens: int = 16384):
        self.encoder = tiktoken.encoding_for_model(model_name)
        self.max_context_tokens = max_context_tokens

    def calculate_tokens(self, text: str) -> int:
        return len(self.encoder.encode(text))

    async def build_safe_context(self, chunks: list, history: list, system_prompt: str) -> str:
        current_tokens = self.calculate_tokens(system_prompt)
        valid_chunks = []
        
        # Сначала резервируем место под историю сообщений (высокий приоритет)
        history_str = json.dumps(history)
        history_tokens = self.calculate_tokens(history_str)
        
        if current_tokens + history_tokens > self.max_context_tokens:
            # История слишком большая, нужно обрезать старые сообщения диалога
            logger.warning("History token budget exceeded, truncating dialogue history")
            # Логика обрезки истории...
        
        current_tokens += history_tokens
        
        # Динамически набиваем контекст чанками из Qdrant, пока есть лимит
        for chunk in chunks:
            chunk_text = f"\nSource [{chunk.payload.get('doc_id')}]: {chunk.payload.get('text')}"

                    "Reached maximum token limit. Dropping remaining low-score chunks.",
                    total_tokens=current_tokens
                )
                break
                
            valid_chunks.append(chunk_text)
            current_tokens += chunk_tokens
            
        return "\n".join(valid_chunks)

1. Сетевой слой ОС: Патологии TCP-стека и Linux-сокетов
Исчерпание портов при агрессивном HTTP-пулинге (TIME_WAIT Exhaustion)
Кейс: Ваш сервис обрабатывает высокий поток параллельных запросов (query_queue). Для генерации ответов воркеры делают сотни асинхронных HTTP-запросов к внешним эндпоинтам (DeepSeek, OpenAI, vLLM, Qdrant).
Проблема: Если в коде инфраструктурных адаптеров (infrastructure/llm/, infrastructure/vector_store/) асинхронный HTTP-клиент (например, httpx.AsyncClient) инициализируется на каждый запрос локально внутри функции (или неправильно сконфигурирован в dishka со scope request вместо app), система начнет плодить тысячи TCP-соединений. При High-Load нагрузке у вас за пару минут закончатся свободные локальные порты эфемерного диапазона (обычно около 28 000 портов). Решение:Настроить HTTP-клиенты в container.py (dishka) строго как синглтоны (Scope.APP). Убедиться, что включен Connection Pooling (параметр limits=httpx.Limits(max_keepalive_connections=..., max_connections=...)).
Тюнинг параметров ядра Linux на хосте (/etc/sysctl.conf): net.ipv4.tcp_tw_reuse = 1 (разрешает повторное использование сокетов в состоянии TIME_WAIT).

Кейс: Пользователь отправляет сообщения в чат-бот очень быстро. Несколько воркеров параллельно обрабатывают запросы по одной и той же conversation_id. Они одновременно пытаются обновить запись беседы в Postgres и вставить новые строки в связанные таблицы источников.

Решение:Использовать конструкцию SELECT ... FOR UPDATE в SQLAlchemy для явной блокировки родительской строки (Conversation) в самом начале пайплайна обработки запроса.

class ProductionLLMClient:

1. Слой инференса: Специфика архитектуры DeepSeek v3/R1 под нагрузкой
Поскольку вашим провайдером по умолчанию является DeepSeek, необходимо учитывать особенности архитектуры моделей класса Mixture-of-Experts (MoE) и рассуждающих моделей (Reasoning/Thinking) в условиях High-Load.
Падение по таймауту из-за раздувания блоков <think> (Thinking Token Exhaustion)
Кейс: Вы отправляете запрос в DeepSeek API. Модель перед генерацией финального ответа запускает скрытый или явный процесс рассуждения (токены внутри тегов <think>...</think>). Запрос оказался сложным, и модель сгенерировала 2000 токенов рассуждений, прежде чем перешла к самому ответу.

В коде парсинга ответа ИИ обязательно очищать или отделять контент внутри тегов <think> перед записью в кэш L1/L2, чтобы не забивать базу «мусорными» логами рассуждений.



2. Слой S3/Файлового хранилища: Аномалии MinIO при пиковых нагрузках
Проблема «Зависших дескрипторов» временных файлов (Tmpfile Disk Bloat)
Кейс: Пайплайн индексации устроен так: «файл скачивается из MinIO во временный каталог -> парсится подходящим парсером -> текст режется на чанки». В систему одновременно загружается пачка из 1000 документов.
Проблема: Если в коде IndexerService для создания временных файлов используется библиотека tempfile или кастомный контекстный менеджер, но при этом в блоке обработки ошибок (except Exception) забыт явный вызов os.unlink(tmp_file_path), то при падении парсера (например, из-за битого PDF) файл останется лежать на диске воркера. Физически диск контейнера забьется временными файлами за несколько дней, и воркер упадет с ошибкой No space left on device, заблокировав всю операционную систему.
Решение: Использовать строго обернутый в try...finally синтаксис удаления файлов, а также подключать встроенный в Python менеджер tempfile.NamedTemporaryFile с флагом delete=True.

3. Слой векторного поиска: Деградация точности при «Проклятии размерности»
Эрозия векторов при ротации коротких/длинных текстов (Chunk Size Imbalance)
Кейс: Парсер нарезает документы на чанки: «текст режется на чанки (~512 символов, по границам слов)». Однако в документе встречаются как полноценные абзацы (512 символов), так и короткие изолированные строки (например, «Итого: 15 000 руб.» или «Утверждаю: Иванов А.В.»). Они тоже превращаются в отдельные чанки и улетают в Qdrant.
Проблема: Модели эмбеддингов (включая используемую вами multilingual-e5-small) очень чувствительны к плотности информации. Маленькие фразы из 2-3 слов в векторном пространстве часто имеют аномально высокую косинусную близость ко многим разнородным запросам. При поиске Qdrant начнет выдавать вам в топ-5 результатов эти «микро-чанки» («Итого:...», «Утверждаю...»), вытесняя длинные информативные абзацы, содержащие реальный контекст. Качество ответов RAG резко упадет.
Решение: Внедрить во внутренний чанкер лимит на минимальный размер чанка (минимальное количество токенов/символов). Маленькие строки не должны становиться отдельными точками в Qdrant — их необходимо склеивать с предыдущим или последующим чанком (паттерн Parent-Child Chunking или Sliding Window Chunking).

4. Пограничные случаи кастомных миграций и реиндекса
Проблема "Замка смерти" при живом реиндексе (Reindex Deadlock Lock)
Кейс: Вы запускаете админ-операцию: «Полный реиндекс коллекции (админ-операция) с логированием миграции версии эмбеддингов». В этот момент reindex_queue создает новую временную коллекцию, начинает вычитывать данные из Postgres и заливать новые векторы в Qdrant. В это же время пользователи продолжают писать в query_queue.
Проблема: Если в процессе реиндекса reindex_worker накладывает тяжелую блокировку (Lock) на таблицу документов в Postgres, чтобы зафиксировать состояние базы на момент миграции, все query-воркеры, пытающиеся записать историю разговора или обновить метаданные, встанут в бесконечную очередь ожидания. Вы получите каскадный таймаут всей системы прямо во время планового обновления.
Решение: Реиндекс должен происходить по паттерну Blue-Green для Vector DB.reindex_worker создает в Qdrant полностью параллельную коллекцию с именем documents_new.
Данные вычитываются из Postgres без блокировок строк (через ленивый асинхронный курсор/пагинацию stream()).
После успешного завершения инвентаризации в коде рантайма атомарно переключается переменная COLLECTION_NAME (или обновляется алиас в Qdrant через команду create_alias), а старая коллекция удаляется в фоновом режиме.



🛠️ Паттерн безопасного Parent-Child чанкинга (src/infrastructure/parsing/)
Реализуем логику фильтрации и склейки «микро-чанков», чтобы защитить векторный поиск Qdrant от эрозии точности:
python

import uuid
import structlog

logger = structlog.get_logger()

class ProductionChunker:
    def __init__(self, chunk_size: int = 512, min_chunk_len: int = 60):
        self.chunk_size = chunk_size
        self.min_chunk_len = min_chunk_len

    def split_text(self, text: str, doc_id: str) -> list[dict]:
        raw_chunks = []
        # Базовая нарезка по символам/словам (имитируем вашу текущую логику)
        words = text.split()
        current_chunk = []
        current_len = 0
        
        for word in words:
            current_chunk.append(word)
            current_len += len(word) + 1
            if current_len >= self.chunk_size:
                raw_chunks.append(" ".join(current_chunk))
                current_chunk = []
                current_len = 0
        if current_chunk:
            raw_chunks.append(" ".join(current_chunk))

        processed_points = []
        buffer_chunk = ""

        # КРИТИЧНО ДЛЯ HIGH-LOAD: Склейка слишком мелких фрагментов
        for idx, chunk in enumerate(raw_chunks):
            combined_text = buffer_chunk + " " + chunk if buffer_chunk else chunk
            combined_text = combined_text.strip()

            if len(combined_text) < self.min_chunk_len and idx < len(raw_chunks) - 1:
                # Чанк слишком мал (например, "Итого: 15к"), копим его в буфер
                buffer_chunk = combined_text
                continue
            
            # Генерируем ваш детерминированный UUID5
            chunk_uuid = str(uuid.uuid5(uuid.NAMESPACE_DNS, f"{doc_id}:{idx}"))
            
            processed_points.append({
                "id": chunk_uuid,
                "text": combined_text,
                "chunk_idx": idx
            })
            buffer_chunk = "" # Сбрасываем буфер

        # Если в самом конце остался мелкий хвостик, принудительно добавляем его
        if buffer_chunk and processed_points:
            processed_points[-1]["text"] += " " + buffer_chunk

        return processed_points




1. Слой очередей: Феномен «Застревания» очередей и TCP Backpressure
Падение производительности aio-pika из-за бесконечного создания Tasks (Task Bloat)
Кейс: Вы используете WORKER_QUEUES=all или query под высокой нагрузкой. aio-pika по умолчанию при вызове queue.consume(callback) на каждое входящее сообщение создает новую асинхронную задачу (asyncio.create_task) в фоновом режиме.
Проблема: Если вызовы к LLM или базам данных начинают обрабатываться дольше обычного (например, DeepSeek временно увеличил latency ответа до 15 секунд), а сообщения продолжают поступать из RabbitMQ с высокой скоростью, количество одновременно запущенных, но незавершенных задач asyncio.create_task внутри одного воркера начнет исчисляться тысячами. Event loop тратит всё больше времени на переключение контекста между этими задачами. Память воркера начинает лавинообразно расти, пока процесс не упадет по сигналу SIGKILL.
Решение: Явное использование семафоров (asyncio.Semaphore) внутри callback-функции воркера для ограничения максимального количества одновременно выполняющихся асинхронных задач в памяти до разумного предела (например, max_concurrent_tasks = 20).

2. Слой СУБД: Эффект «Хвоста» при пагинации больших таблиц
Деградация асинхронных курсоров Postgres при реиндексе (Cursor Erosion)
Кейс: Во время выполнения reindex_queue вы запускаете асинхронное чтение из PostgreSQL через SQLAlchemy await session.stream(statement). В таблице documents накопились миллионы записей.
Проблема: Асинхронные серверные курсоры (asyncpg) удерживают снимок данных на момент открытия транзакции. Если процесс реиндекса и пересчета эмбеддингов для всей базы занимает несколько часов, Postgres вынужден сохранять старые версии изменяемых строк в области MVCC (Multi-Version Concurrency Control). Это приводит к резкому росту нагрузки на подсистему ввода-вывода (I/O) сервера БД, замедлению всех остальных параллельных read/write запросов от query-воркеров и раздуванию дискового пространства базы.
Решение: Отказаться от долгоживущих курсоров при массовых операциях. Заменить stream() на пагинацию по базовому ключу (Keyset Pagination): SELECT * FROM documents WHERE id > :last_id ORDER BY id LIMIT 1000. Такой запрос выполняется атомарно, быстро закрывает транзакции и не создает паразитной нагрузки на MVCC.

3. Слой векторного поиска: Специфика сборщика мусора и буферов Qdrant
Падение воркера при gRPC-стриминге точек (Out of Memory on Scroll)
Кейс: Админ-скрипт или воркер реиндекса пытается вычитать все существующие точки из коллекции Qdrant для проведения аудита или миграции через метод client.scroll().
Проблема: Метод scroll возвращает пачку точек вместе с их векторами и тяжелым payload (включая HTML-структуры таблиц). Если размер страницы (limit) выставлен слишком большим (например, 10 000 точек), асинхронный gRPC-клиент Qdrant попытается аллоцировать гигантский кусок памяти под десериализацию Protobuf-сообщения. В условиях высокой нагрузки на кучу (Heap) Python это приводит к мгновенной фрагментации памяти и падению процесса по OOM, даже если физически на сервере есть свободная RAM.
Решение: При выполнении операций scroll выставлять размер страницы (limit) не более 100–500 элементов и явно запрашивать исключение векторов из ответа (with_vectors=False), если они не нужны для текущей логики миграции.

4. Пограничные случаи сетевой топологии: DNS-шторм
Зависание асинхронных клиентов при таймаутах DNS (Async DNS Resolution Blocking)
Кейс: Сервис развернут в Kubernetes или Docker Compose. Внешние LLM API вызываются по доменным именам (например, ://deepseek.com). При пиковых нагрузках воркеры делают сотни сетевых запросов в секунду.
Проблема: По умолчанию библиотека httpx использует стандартный системный резолвер DNS, который в Python работает в синхронном режиме через getaddrinfo. При обрыве связи с DNS-сервером или высокой нагрузке на CoreDNS внутренний поток Python блокируется на время ожидания ответа DNS (системный таймаут может составлять до 5–30 секунд). В этот момент асинхронный воркер полностью застывает, переставая обрабатывать любые другие задачи в event loop, включая healthcheck-запросы.
Решение: Использовать асинхронный резолвер DNS. Для этого при инициализации httpx.AsyncClient необходимо явно передавать специализированный транспорт или настраивать библиотеку aiodns, которая выполняет DNS-запросы полностью асинхронно через неблокирующие сокеты.

🛠️ Паттерн безопасной Keyset-пагинации для реиндекса (src/infrastructure/repositories/)
Реализуем паттерн неблокирующего чтения больших объемов метаданных из PostgreSQL без создания долгоживущих серверных курсоров:
python

from sqlalchemy import select
from src.infrastructure.repositories.models import DocumentORM

class ProductionDocumentRepository:
    def __init__(self, session_factory):
        self.session_factory = session_factory

    async def get_all_documents_generator(self, batch_size: int = 500):
        """
        Безопасный генератор для High-Load реиндекса.
        Не блокирует MVCC Postgres и не раздувает память воркера.
        """
        last_id = 0
        
        while True:
            # Открываем короткую изолированную транзакцию на каждый батч
            async with self.session_factory() as session:
                query = (
                    select(DocumentORM)
                    .where(DocumentORM.id > last_id)
                    .order_by(DocumentORM.id)
                    .limit(batch_size)
                )
                result = await session.execute(query)
                batch = result.scalars().all()
                
                if not batch:
                    break  # Все данные вычитаны
                
                for doc in batch:
                    yield doc
                    last_id = doc.id  # Фиксируем последний обработанный ID
                    
            # Короткая пауза между батчами для того, чтобы дать asyncio 
            # возможность обработать другие сетевые задачи (I/O Yielding)
            await asyncio.sleep(0.01)
